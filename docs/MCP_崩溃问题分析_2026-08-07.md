# Aegisub MCP 崩溃问题分析与修复记录

- 日期：2026-08-07
- 状态：已修复并验证
- 影响范围：Aegisub 核心（`subs_controller.cpp`、`base_grid.cpp`），与 MCP 工具本身无关
- 触发场景：打开含 `[Aegisub Project Garbage]` 段的字幕文件 + 加载视频后，执行"新建字幕"（MCP `new_file` 或 GUI `subtitle/new`）

## 1. 现象

执行 MCP `new_file` 工具（或 GUI 菜单"新建字幕"）时，Aegisub 进程以 `0xC0000005`（访问违例）崩溃：

- crash writer 在 `%APPDATA%\Aegisub\crashdumps\` 生成 minidump（如 `3.4.7-2026-08-07-07-23-16-27084.dmp`）
- MCP HTTP 请求得到 502/连接重置（`Invoke-RestMethod` 报 `Response status code does not indicate success: 502 (Bad Gateway)`）
- MCP server 线程随进程消亡，后续请求全部失败，**只能重启 Aegisub**

崩溃表现为**间歇性**：同一操作序列有时崩溃、有时正常（实测约 1/3 ~ 7/8 概率，与内存布局和时序相关）。

## 2. 触发条件

经逐项实验确认的最小触发组合：

| 条件                                  | 必需 | 说明                                                       |
|-------------------------------------|----|----------------------------------------------------------|
| 字幕文件含 `[Aegisub Project Garbage]` 段 | 是  | 段内任意字段（`Video Position`、`Scroll Position` 等）均可触发，字段值无关紧要 |
| 加载过视频                               | 是  | `open_video`（手动或自动加载均可），关闭与否不影响                          |
| 执行新建字幕                              | 是  | `new_file` / `subtitle/new` / `CloseSubtitles` 路径        |

不触发的情况：

- 不含 Garbage 段的字幕文件（如 Aegisub 默认新建文件）
- 未加载视频
- 仅执行 `open_file`/`open_video`/`close_video` 等单步操作（单独调用均正常）

## 4. 排查过程

### 4.1 阶段一：怀疑 CSRI/VSFilterMod 插件释放

用户配置 `Subtitle/Provider = "CSRI/2026.07.08.1458"`（VSFilterMod64.dll），且用户此前开发 VSFilterMod 时已知"释放插件会崩溃"，故首先怀疑插件路径。

排查结论（**排除**）：

- libcsri（`subprojects/csri/lib/win32/enumerate.c`）仅在 DLL **加载失败**时 `FreeLibrary`，正常加载的渲染器 DLL **常驻进程**，`close_video`/`new_file` 不会卸载插件
- `CSRISubtitlesProvider` 析构会调用插件的 `csri_close`（释放字幕实例），但该路径在无视频/关视频时均正常
- **决定性实验**：把 `Subtitle/Provider` 临时切换为 `libass` 后，崩溃依旧复现 → 与渲染插件无关（实验后已恢复配置）

### 4.2 阶段二：字段二分

对比用户文件与 Aegisub 默认新建文件的差异，逐字段构造测试文件：

| 测试文件                   | Garbage 字段      | 结果                                            |
|------------------------|-----------------|-----------------------------------------------|
| 无 Garbage 段（空行文件）      | 无               | 不崩                                            |
| `Video Position: 425`  | Video Position  | 崩（3/4）                                        |
| `Scroll Position: 173` | Scroll Position | 崩（4/4，修复前）                                    |
| `Video AR Mode/Value`  | AR              | 未测完（实例已崩）                                     |
| `Video File: <mkv>`    | Video File      | open_file 即触发关联文件自动加载（Load Linked Files=2 弹窗） |

结论：**`[Aegisub Project Garbage]` 段的存在本身**即触发条件，字段内容无关。这也解释了为何"Video Position"最初被误判为特异字段——它只是改变了提交时序/内存布局，使崩溃从"偶发"变为"必现"。

### 4.3 阶段三：minidump 分析

用 Python `minidump` 库解析崩溃 dump（`3.4.7-2026-08-07-07-23-16-27084.dmp`）：

- 异常：`EXCEPTION_ACCESS_VIOLATION (0xC0000005)`，异常地址 `0x7FFE...`（模块代码区）
- 栈扫描：KERNELBASE.dll（栈顶）+ msvcp140.dll（C++ 异常运行时）+ ntdll + Aegisub.exe + user32/uxtheme
- 特征：**C++ 异常栈展开过程中的访问违例**（msvcp140 的 `__CxxFrameHandler` 参与），与"信号回调内访问已销毁对象"一致
- 局限：crash writer 未写线程上下文（Rip/Rsp 为 0），无法直接回溯调用栈

### 4.4 阶段四：日志定位（踩坑记录）

Aegisub 日志（`%APPDATA%\Aegisub\log\*.json`）用于定位：

- **踩坑**：`LogSink::Log`（`libaegisub/common/log.cpp:45`）是 `queue->Async` **异步投递**，崩溃时最后几条日志可能未写入 → 日志显示"崩溃在 FileOpen 前"的结论**不可靠**
- 改用**同步文件标记法**：在 `HandleNewFile` → `Project::CloseSubtitles` → `SubsController::Close` → `AssFile::Commit` 的关键步骤写临时文件（`std::ofstream`），逐层缩小范围

定位结果（崩溃轮的标记文件内容）：

```
new_file: after CloseVideo / after CloseAudio / after CloseTimecodes / after CloseKeyframes
CloseSubtitles: 0 enter
SubsController::Close: 0 enter / 1 stacks cleared / 2 swapped / 3 LoadDefault
（崩溃发生在 Commit("", COMMIT_NEW) 内）
```

进一步在 `AssFile::Commit` 内部加标记：

```
A after PreCommit
B after PushState
（崩溃在 AnnounceCommit 之前 → 即 PushState 或 AnnounceCommit 的信号链）
```

### 4.5 阶段五：信号链分析

`AssFile::Commit`（`src/ass_file.cpp`）：

```cpp
AnnouncePreCommit(type, single_line);
PushState({desc, &amend_id, single_line});   // → SubsController::OnCommit
AnnounceCommit(type, single_line);           // → 10 个监听器
```

`AnnounceCommit` 监听器（按注册顺序）：

- `AudioKaraoke::OnFileChanged`、`AudioTimingControllerDialogue::OnFileChanged`（音频未加载）
- `BaseGrid::OnSubtitlesCommit`（网格刷新，**重点嫌疑**）
- `DialogTranslation::OnExternalCommit`、`DialogStyleManager::LoadCurrentStyles`
- `FrameMain::UpdateTitle`、`SubsEditBox::OnCommit`
- `VideoBox::UpdateTimeBoxes`、`VideoController::OnSubtitlesCommit`（视频已关，`!provider` 提前返回）
- `VisualToolBase::OnCommit`

**根因**：`SubsController::Close()` 的执行顺序存在窗口期：

```cpp
AssFile blank;
blank.swap(*context->ass);          // ① 旧字幕行移出 Events（进入 blank）
context->ass->LoadDefault(...);     // ② 生成新行
context->ass->Commit("", COMMIT_NEW); // ③ ★ 此时 selection 仍指向旧行
```

在 ③ 的信号链中，`BaseGrid::OnSubtitlesCommit`、`SubsEditBox::OnCommit` 等监听器会读取当前选中/活动行（`selectionController->GetActiveLine()`），而该指针在 ① 之后已悬空（对象随 `blank` 析构或移出 `Events`）→ 访问违例。

## 5. 根因详解

### 5.1 悬空 selection（主因）

- `SelectionController` 保存 `AssDialogue*` 指针（`std::set<AssDialogue*>` + active line）
- `Close()` 的 `swap` 把旧行移出 `context->ass->Events`，旧行对象生命周期结束（`blank` 析构时随 auto_unlink 摘除，heap 对象泄漏但不释放——**但指针已不再指向 Events 内的有效行**）
- `Commit("", COMMIT_NEW)` 触发 `AnnounceCommit`，网格/编辑框监听器访问 selection 中的悬空指针 → 0xC0000005

### 5.2 为什么间歇性

崩溃点位于信号链中多个监听器对悬空指针的访问，是否崩溃取决于：

- 悬空内存是否恰好被复用/改写（内存布局）
- 监听器对该指针的访问深度（只比较指针 vs 解引用成员）
- Garbage 段改变 `Properties` 内容 → 改变后续提交的 `commit_id` 时序 → 改变是否进入 `OnCommit` 的 coalescing 分支（空栈 `pop_back` UB）→ 改变内存破坏程度 → 崩溃概率显著变化

### 5.3 为什么 Garbage 段必现

含 Garbage 段时 `Properties` 非零，`LoadUnloadFiles` 等路径的提前返回条件、`commit_id`/`saved_commit_id` 序列均与无 Garbage 段不同，导致空 undo 栈上的 `pop_back()` 必被触发一次，先损坏 `boost::container::list` 内部哨兵节点，随后任何一次后续提交即崩溃。无 Garbage 段时该 UB 不触发（或触发后恰未损坏关键内存），表现为偶发。

## 6. 修复内容

### 6.1 `SubsController::Close()` — 先 Commit 重建网格缓存，再切换 selection（主修复）

`src/subs_controller.cpp`：

```cpp
void SubsController::Close() {
	undo_stack.clear();
	redo_stack.clear();
	autosaved_commit_id = saved_commit_id = commit_id + 1;
	filename.clear();
	AssFile blank;
	blank.swap(*context->ass);
	context->ass->LoadDefault(true, OPT_GET("Subtitle Format/ASS/Default Style Catalog")->GetString());
	// 先 Commit 让 BaseGrid 等监听器把行缓存（vis_index_line_map）重建到新文件，
	// 再切换选中/活动行。若顺序颠倒，BaseGrid::OnActiveLineChanged 的
	// MakeRowVisible 会用指向旧文件行的悬空缓存，且旧行已不在 Events 中。
	// Commit 信号链访问 selection 时旧行对象仍存活（blank 作用域内），是安全的。
	context->ass->Commit("", AssFile::COMMIT_NEW);
	if (!context->ass->Events.empty()) {
		auto line = &*context->ass->Events.begin();
		context->selectionController->SetSelectionAndActive({line}, line);
	}
	FileOpen(filename);
}
```

**两轮修复的演进**（重要）：

- **第一版**（Commit 前切 selection）：解决了"Commit 信号链访问已移出 Events 的 selection"的崩溃，但引入了新崩溃——`SetSelectionAndActive` 触发 `BaseGrid::OnActiveLineChanged → MakeRowVisible(new_active->Row) → GetDialogue(row)`，而网格的 `vis_index_line_map` 缓存**仍是 swap 前的旧文件行**（`COMMIT_NEW` 才会触发 `UpdateMaps()` 重建缓存），且 `active_row` 非 0 时 `MakeRowVisible` 必被执行 → 访问悬空缓存崩溃
- **最终版**（先 Commit 后切 selection）：`Commit("", COMMIT_NEW)` 先触发 `BaseGrid::OnSubtitlesCommit → UpdateMaps()` 把行缓存重建到新文件；此时 selection 仍指向旧行，但旧行对象在 `blank` 作用域内**仍存活**，信号链对其只做指针比较/读取，安全；随后 `SetSelectionAndActive` 使用**新缓存**，`MakeRowVisible` 访问有效行

### 6.2 `SubsController::OnCommit()` — 空 undo 栈保护（附带修复）

`src/subs_controller.cpp`：

```cpp
// 注意：Close()/Load() 清空 undo 栈后可能提交空 message 的 Commit，
// 此时栈为空，back()/pop_back() 是未定义行为，必须跳过合并
if (!undo_stack.empty() && commit_id == *c.commit_id+1 && redo_stack.empty() && saved_commit_id+1 != commit_id) {
```

原理：coalescing 分支假设 undo 栈至少有一个元素（初始状态在栈底），但 `Close()`/`Load()` 先 `clear()` 后提交空 message 的 `Commit`，破坏该假设。

### 6.3 `BaseGrid::ScrollTo()` — clamp 未定义行为保护（防御性修复）

`src/base_grid.cpp`：

```cpp
void BaseGrid::ScrollTo(int y) {
	int max_row = GetVisRows() - 1;
	// 网格尚未就绪（无可视行）时忽略滚动请求，
	// 否则 std::clamp 在 lo(0) > hi(-1) 时是未定义行为
	if (max_row < 0)
		return;
	int nextY = std::clamp(y, 0, max_row);
	...
}
```

原理：打开文件早期网格未布局（`GetVisRows()==0`）时，`std::clamp(y, 0, -1)` 的 lo>hi 是标准库未定义行为。

### 6.4 `HandleDeleteSubtitleLine` — 删除后重建 selection（审查修复）

`src/mcp_server.cpp`：删除行后若选中/活动行已被删，`SelectionController` 会持有指向已释放对象的悬空指针（与 `Close` 悬空问题同类，删除操作是 MCP 自动化最常规序列）。修复：删除 + Commit 后，从剩余行过滤重建 selection，为空则选第一行，活动行不在选中集则取第一个。

### 6.5 `HandleUpdateStyle` — 防部分应用（审查修复）

`src/mcp_server.cpp`：`ApplyStyleFields` 直接应用到活对象，若颜色解析中途失败会导致样式被改一半且无撤销记录。修复：新增 `ValidateStyleFields()` 预先验证会抛异常的字段（颜色解析），通过后再应用。注意**不能**用临时 `AssStyle` 副本方案——已链接的 `AssStyle` 拷贝会浅拷贝 intrusive hook，临时对象析构时 auto_unlink 破坏 `Styles` 链表（实测崩溃，与 6.1 同源）。

### 6.6 其他审查修复

- `time_to_ms`：`agi::Time` 对非法字符静默跳过不抛异常，原 `catch` 分支是死代码；改为显式校验输入字符集
- `DoLoadVideo` 非交互模式：`UserCancelException` 同样重抛，避免误报旧视频"打开成功"
- `get_audio_spectrum` 描述：实际峰值约 1.9~2.9（log10 归一化与 GUI 一致），修正 "0~1" 的错误描述

**残留风险说明（最终结论：已根除）**：

经 CLion 调试器（MCP xdebug）拿到真实调用栈后，最终根因定位并修复：

**根因**：MCP `open_file` 直接调用 `subsController->Load()`，与 GUI 的 `DoLoadSubtitles`
不同——**没有加载后更新选中/活动行**（GUI 路径在 `DoLoadSubtitles` 末尾
`SetSelectionAndActive` 更新）。`Load` 内部 `swap` 把旧字幕行移入局部 `temp`，
`temp` 析构时 `AssFile::~AssFile` 的 `clear_and_dispose` **delete 全部行对象**，
而 `SubsEditBox::line` 缓存仍指向已删除的旧行（悬空）→ 后续任何 `Commit`
（如 `new_file` 的 `Commit("", COMMIT_NEW)`）触发 `SubsEditBox::OnCommit`
（subs_edit_box.cpp:389）读取 `line->Style` → `GetStyle` 的 `boost::iequals`
访问悬空字符串 → 0xC0000005。间歇性源于已释放内存是否被复用。

**调试器定位证据**（CLion MCP `xdebug_get_stack` 真实栈）：
```
SubsEditBox::OnCommit (subs_edit_box.cpp:389)
  → AssFile::GetStyle (ass_file.cpp:188)  ← boost::iequals 中 std::string 访问违例
  ← AssFile::Commit ← SubsController::Close ← CloseSubtitles ← HandleNewFile
```
帧 19 求值：`line->Row = 32761`（垃圾值）、`line->Text = "2026.07.08.1640"`（版本号）——
**line 指向的内存已被完全复用**，确认悬空。

**修复**：`HandleOpenFile` 在 `Load` 后补充 `SetSelectionAndActive`（与
`DoLoadSubtitles` 一致），使 `SubsEditBox::line` 等组件缓存指向新文件的有效行。

**验证**：修复后 Garbage 文件+new_file 20/20、用户文件+视频+new_file 10/10、
用户文件+行 CRUD+new_file 10/10 全部通过（修复前 10%~40% 崩溃率），零崩溃。

**调试方法备忘**：CLion MCP（streamable-http，先 `initialize` 拿 `Mcp-Session-Id`）：
`xdebug_start_debugger_session`（configurationName=Aegisub）→
`xdebug_set_breakpoint`（main.cpp:546 `AegisubApp::UnhandledException`，
注意 Release 优化会内联小函数导致断点无效，选大函数）→ 复现 →
`xdebug_get_stack` / `xdebug_get_frame_values` / `xdebug_evaluate_expression`
（evaluate 需带 threadId+frameIndex）抓栈与变量。

## 8. MCP 与进程崩溃的边界（结论）

MCP 的异常处理（`agi::Exception`/`std::exception` 捕获 → JSON-RPC error）**只能覆盖可抛出的 C++ 异常**：

- handler 抛异常 → `server.cpp` catch 链 → `-32603` JSON-RPC error，消息透传
- 进程级崩溃（SEH `0xC0000005`）**不经 C++ catch 链** → crash writer 写 minidump → 进程退出 → HTTP 连接断开（502/连接重置）→ **无法恢复，只能重启 Aegisub**

MCP 侧无法拦截进程崩溃，因此排查此类问题时必须以"Aegisub 核心代码 bug"为出发点（本次即如此），修复核心代码后 MCP 自动受益。
